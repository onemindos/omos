# Messages & Headers

> **Core idea.** A NATS message is a simple envelope — subject, optional reply address, optional headers, and a binary payload. Headers follow an HTTP/1.x-like format prefixed with `NATS/1.0`. Understanding message anatomy is essential for reading the wire protocol, debugging, and using advanced features like deduplication, tracing, and no-responders.

See [[NATS/01-CORE-CONCEPTS/publish-subscribe|Publish/Subscribe]] for how messages flow.  
See [[NATS/10-PROTOCOL-INTERNALS/README|Protocol Internals]] for full wire-format specification.

---

## 1. Message Anatomy

Every NATS message consists of exactly four fields:

| Field | Required | Description |
|-------|----------|-------------|
| **Subject** | ✅ Yes | Destination address — a dot-separated subject string |
| **Payload** | No (can be empty `0` bytes) | Arbitrary byte array; the message body |
| **Headers** | No | Key-value metadata in NATS/1.0 HTTP-like format |
| **Reply-to** | No | Subject for the responder to publish back to (used in request/reply) |

```
┌────────────────────────────────────────────┐
│  Subject:   orders.created                 │ ← required
│  Reply-to:  _INBOX.abc123xyz789            │ ← optional
│  Headers:                                  │ ← optional
│    NATS/1.0\r\n                            │
│    Nats-Msg-Id: order-42\r\n               │
│    Content-Type: application/json\r\n      │
│    \r\n                                    │
│  Payload:   {"orderId":"42","total":99.95} │ ← optional byte array
└────────────────────────────────────────────┘
```

## 2. Payload

### Size Limits

| Config | Default | Maximum |
|--------|---------|---------|
| `max_payload` | **1 MB** (1,048,576 bytes) | 64 MB (67,108,864 bytes) |
| Recommended max | — | ≤ 8 MB (per official docs) |

Set in the server configuration:

```hcl
# nats-server.conf
max_payload: 8MB
```

> **Design guidance:** For large payloads (images, files), use [[NATS/03-KV-OBJECT-STORE/README|Object Store]] (JetStream) and publish only the reference/metadata on the subject. Keep message payloads small for high throughput and low latency.

### Encoding

Payloads are opaque byte arrays. NATS does not interpret encoding. Convention:
- **JSON** — most common for structured data; use `Content-Type: application/json` header
- **Protocol Buffers / MessagePack** — for high-performance binary
- **Plain text / plain bytes** — for simple values

## 3. Headers (NATS/1.0)

Headers were added in NATS server **v2.2.0** (2021). They use an HTTP/1.x-inspired format.

### Format

```
NATS/1.0\r\n
Header-Name: value\r\n
Another-Header: value\r\n
\r\n
```

**Rules:**
- First line must be `NATS/1.0` followed by `\r\n` (or optionally a status code, see §3.2 below).
- Each header is `Name: Value\r\n`.
- Header names are case-insensitive.
- **Multi-value headers** are allowed: repeat the same header name.
- Headers block is terminated by `\r\n\r\n` (blank line).
- Header size is counted separately from payload size.

### Example — full HPUB wire message

```
HPUB FRONT.DOOR JOKE.22 45 56\r\n
NATS/1.0\r\n
BREAKFAST: donut\r\n
LUNCH: burger\r\n
\r\n
Knock Knock\r\n
```

Where:
- `FRONT.DOOR` = subject
- `JOKE.22` = reply-to
- `45` = header byte count (including `NATS/1.0\r\n...` through terminal `\r\n`)
- `56` = total byte count (header bytes + payload bytes)

### Multi-value header example

```
HPUB MORNING.MENU 47 51\r\n
NATS/1.0\r\n
BREAKFAST: donut\r\n
BREAKFAST: eggs\r\n
\r\n
Yum!\r\n
```

## 3.2 Status Headers (Special NATS/1.0 Lines)

NATS uses the `NATS/1.0` version line to carry **status codes** in certain protocol messages. These are synthetic messages generated by the server, not by applications.

| Status line | Meaning |
|-------------|---------|
| `NATS/1.0 503\r\n` | **No Responders** — published to a subject with no subscribers |
| `NATS/1.0 404\r\n` | Not found (used in KV / JetStream contexts) |
| `NATS/1.0 408\r\n` | Request timeout (JetStream fetch) |
| `NATS/1.0 100\r\n` | Idle heartbeat (JetStream push consumer) |
| `NATS/1.0 409\r\n` | Conflict / exceeded limits (JetStream) |

### No-Responder Header (503)

When a client sends a request to a subject with no subscribers and has opted into `no_responders`, the server immediately replies with a synthetic status message:

```
HMSG _INBOX.abc123 <sid> 16 16\r\n
NATS/1.0 503\r\n
\r\n
\r\n
```

The client library translates this to `nats.ErrNoResponders`. See [[NATS/01-CORE-CONCEPTS/request-reply#6-no-responders-instant-503|Request/Reply → No Responders]].

## 4. Well-Known NATS Headers

These headers have specific meanings in NATS server and official client libraries:

| Header | Used By | Meaning |
|--------|---------|---------|
| `Nats-Msg-Id` | JetStream dedup | Unique message ID for deduplication window |
| `Nats-Expected-Stream` | JetStream | Assert the target stream before publishing |
| `Nats-Expected-Last-Msg-Id` | JetStream | Optimistic concurrency check |
| `Nats-Expected-Last-Sequence` | JetStream | Assert last sequence number |
| `Nats-Rollup` | JetStream KV | Subject-level or all-subjects rollup |
| `Nats-Stream` | JetStream consumer | Stream name (set by server on delivered message) |
| `Nats-Sequence` | JetStream consumer | Stream sequence of delivered message |
| `Nats-Time-Stamp` | JetStream consumer | Server timestamp of stored message |
| `Nats-Subject` | JetStream consumer | Original subject |
| `Nats-Pending` | JetStream consumer | Remaining messages for this consumer |
| `Nats-Last-Consumer` | JetStream consumer | Consumer's last delivered sequence |
| `Nats-Last-Stream` | JetStream consumer | Stream's last sequence at time of delivery |
| `Nats-Consumer` | JetStream consumer | Consumer name |
| `Nats-Ack-Domain` | JetStream | JetStream domain for ack |
| `traceparent` | OTEL / msg tracing | OpenTelemetry trace context (W3C) |
| `Content-Type` | Application | MIME type of payload (convention, not enforced) |

## 5. Using Headers in Client Code

### Go — publish with headers

```go
msg := &nats.Msg{
    Subject: "orders.created",
    Header:  nats.Header{},
    Data:    []byte(`{"orderId":"42"}`),
}
msg.Header.Set("Content-Type", "application/json")
msg.Header.Set("Nats-Msg-Id", "order-42")   // JetStream dedup

if err := nc.PublishMsg(msg); err != nil {
    log.Fatal(err)
}
```

### Go — read headers from received message

```go
nc.Subscribe("orders.created", func(m *nats.Msg) {
    contentType := m.Header.Get("Content-Type")
    msgId := m.Header.Get("Nats-Msg-Id")
    log.Printf("ct=%s id=%s body=%s", contentType, msgId, m.Data)
})
```

### Python — headers (nats.py v2.x)

```python
import nats
from nats.aio.client import Client as NATS

async def main():
    nc = await nats.connect("nats://localhost:4222")

    # Publish with headers
    await nc.publish(
        "orders.created",
        b'{"orderId":"42"}',
        headers={
            "Content-Type": "application/json",
            "Nats-Msg-Id": "order-42",
        }
    )

    # Receive with headers
    async def handler(msg):
        print("headers:", msg.headers)
        print("data:", msg.data.decode())

    await nc.subscribe("orders.created", cb=handler)
```

## 6. Protocol Wire Commands

### Without Headers: `PUB` / `MSG`

```
# Client publishes (no headers)
PUB <subject> [reply-to] <#bytes>\r\n
[payload]\r\n

# Example:
PUB orders.created 29\r\n
{"orderId":"42","total":99.95}\r\n

# Server delivers to subscriber
MSG <subject> <sid> [reply-to] <#bytes>\r\n
[payload]\r\n
```

### With Headers: `HPUB` / `HMSG`

```
# Client publishes (with headers)
HPUB <subject> [reply-to] <#header bytes> <#total bytes>\r\n
NATS/1.0\r\n
[Header-Name: value\r\n]...
\r\n
[payload]\r\n

# Example:
HPUB orders.created 34 63\r\n
NATS/1.0\r\n
Nats-Msg-Id: order-42\r\n
\r\n
{"orderId":"42","total":99.95}\r\n

# Server delivers to subscriber
HMSG <subject> <sid> [reply-to] <#header bytes> <#total bytes>\r\n
NATS/1.0\r\n
[headers]\r\n
\r\n
[payload]\r\n
```

> **`#header bytes`** counts from the start of `NATS/1.0` through and including the final `\r\n` of the blank line.  
> **`#total bytes`** = header bytes + payload bytes.

## 7. Summary Table

| Field | Protocol position | Wire command (no headers) | Wire command (with headers) |
|-------|-------------------|--------------------------|----------------------------|
| Subject | First | `PUB <subject>` | `HPUB <subject>` |
| Reply-to | Optional, second | `[reply-to]` | `[reply-to]` |
| Header size | N/A | N/A | `<#header bytes>` |
| Total size | Third | `<#bytes>` | `<#total bytes>` |
| Headers | N/A | — | `NATS/1.0\r\n...\r\n\r\n` |
| Payload | After `\r\n` | `[payload]\r\n` | `[payload]\r\n` |
