# Existing-platform discovery before recommending another app

- Inventory live Deployments, StatefulSets, Pods, Services and ArgoCD Applications before proposing new control planes. Save sanitized batches and aggregate in code. Never retrieve/print Secret values as inventory.
- If kubectl is unavailable inside the pod, use Python stdlib HTTPS to the Kubernetes API with the service-account CA and bearer token. Send that token only to the Kubernetes API, never to application service URLs. Do not weaken RBAC or network policies to complete an inspection. Sanitize before saving: retain workload identities, images, readiness and selected source/provenance fields; omit env values, Secret data, complete ConfigMaps and arbitrary embedded chart values. Reduce ArgoCD sync state to status/revision fields because comparedTo can contain configuration that is unnecessary for the audit.
- Do not infer a running product from a namespace, a completed Job, a dependency declaration or an old report. Verify live workloads/services and deployed features; empty leftover namespaces can survive a product removal.
- Look for the first-party application source in onemindos/omos: services/onemind-portal and services/onemind-core, plus platform/hermes/agent-fabric. Treat these paths as discovery hints, not proof of current deployment.
- Read ArgoCD source path and sync revision, inspect manifests pinned to that revision and compare the deployed frontend bundle. ArgoCD revision alone does not attest the source commit of an image; image provenance and actual runtime behavior are separate checks.
- The portal may be a custom operations app with /missions, /today and /assistant rather than a generic Backstage catalog. Its core may already contain PostgreSQL mission state, Dapr workflows, a transactional NATS/JetStream outbox, Synadia discovery/delegation, and OpenFGA capability authorization. Verify these in the current source and live deployment before recommending a replacement.
- Ready replicas are not application workflow verification. A namespace, cleanup Job or archived manifest is not a running application; check current controllers, Services, Pods and GitOps ownership before asserting a stack is deployed. A SPA catch-all returning HTML 200 for /healthcheck is not a genuine health endpoint. For Backstage, probe /.backstage/health/v1/readiness and verify JSON content separately from the HTML root and authenticated APIs. Treat a catalog HTTP 401 or ConfigMap/CRD HTTP 403 as an inspection boundary, not an outage or evidence of absent data.
- If internal HTTP probes time out, inspect namespace NetworkPolicies; preserve intended isolation. If authentication blocks a page, report the boundary rather than treating it as an app outage or bypassing it.
- Separate operator authorization from a persistent per-command approval inbox. Verify external execution cancellation rather than assuming termination of an orchestration workflow stops the dispatched work. Inspect query/approval frame handling in any agent bridge.
- Verify first-class task/routine/recurrence/notification and person/project privacy features independently of a generic object/relationship store. Existing mission CRUD does not establish a Todoist replacement or safe household roles.
- Keep Paperclip's active work until migration criteria pass. Existing n8n/connectors can assist without becoming a competing work authority. Do not call optional Nextcloud apps installed merely because the server is ready.
- A local legacy mission-engine manifest marked planned/replicas zero is not a running mission engine. Check the live API; distinguish it from onemind-core.
- If broad search_files fails, diagnose once and narrow to the repository. git ls-files can discover tracked paths. Avoid scanning giant vaults unnecessarily and never expose sensitive matching files just because their names appear in a listing.
