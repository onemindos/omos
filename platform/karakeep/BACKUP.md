# Karakeep persistence and recovery gate

The initial encrypted snapshots and local SQLite restore integrity were verified on 2026-10-25, as recorded below. This proves the initialized SQLite structures can be recovered from the encrypted repository; a full application/owner/attachment restore remains a separate acceptance check. The existing VolSync/Restic pipeline has two app-owned sources. The full `/data` volume is authoritative: SQLite, its journals/WAL, assets/attachments, background-job state and related app files belong together. Keep the strict SealedSecrets and the cluster sealing-key recovery separately. User bookmark JSON/ZIP exports produced by the app are useful portability exports, not a complete users/config/assets disaster-recovery backup.

## Deployed source policy

`karakeep-data` runs at 12:40 UTC daily and `karakeep-meilisearch` at 13:00 UTC daily. Both use the installed VolSync 0.16.0 operator, Snapshot copy method, existing DigitalOcean CSI `do-block-storage` snapshot/storage classes, one 1Gi cache each and non-root UID/GID1000 movers. Each mover requests 100m CPU / 256Mi memory with a 1 CPU / 1Gi limit. Namespace egress permits DNS and HTTPS to the existing S3 path, without giving the application access to backup credentials or the Kubernetes API.

Strict namespace-bound SealedSecrets `karakeep-data-restic` and `karakeep-meilisearch-restic` contain the existing authorized Spaces backup credential, fresh independent Restic encryption passwords and distinct repository prefixes:

- `s3:https://nyc3.digitaloceanspaces.com/onemind-backups/backups/restic/karakeep/data-pvc`
- `s3:https://nyc3.digitaloceanspaces.com/onemind-backups/backups/restic/karakeep/meilisearch-pvc`

The existing provider credential is reused without changing its permissions; these are separate repositories, not newly asserted provider-side prefix restrictions. Fresh encryption passwords and the app-only OIDC secret are preserved privately outside Git in the coordinator's task recovery material (mode0600). Preserve an independent recovery copy. The existing app/session and Meilisearch keys are preserved, not rotated. The encrypted cluster-recovery export must include these new secrets before cluster-loss recovery is considered covered.

Retention matches the existing pipeline: 7 daily / 4 weekly / 3 monthly / 1 yearly, with prune every 14 days. **Scheduled snapshots are crash-consistent** full-volume copies, including SQLite WAL/journals. There is no automatic app quiesce hook in the installed CRD, no backup account with workload-scaling rights and no application/DB coordinated-restore claim. Storage is in the same provider/region as the cluster; the independent offsite copy remains a separate platform prerequisite.

## Before real use

1. Record `karakeep/data-pvc` (20Gi) and `karakeep/meilisearch-pvc` (5Gi) UIDs/PVs after manual Argo creation; both use do-block-storage and explicit Prune=false, Delete=false, Replace=false, Force=false protections. Do not delete the namespace or claims on uninstall.
2. Confirm both dedicated SealedSecrets are Synced and both ReplicationSources use the expected repository secret. These AWS-named fields are the existing Restic S3-protocol contract, not AWS service credentials. See the [existing VolSync runbook](../backups/volsync/README.md). Do not print secret values or replace encryption passwords during redeploys.
3. Trigger the initial sources using new `spec.trigger.manual` identifiers through reviewed Git/Argo; retain the daily schedule fields. Wait until any earlier mover is idle before changing the tag, then require matching `status.lastManualSync`, a `lastSyncTime` after web startup and a nonempty Restic snapshot ID. A successful empty-directory skip is not a backup. **VolSync 0.16.0 gives a nonempty manual trigger priority over cron**, so remove `spec.trigger.manual` from both sources in a follow-up reviewed Git change immediately after success; otherwise the daily schedules remain paused. Verify `status.nextSyncTime` returns after removal. An imperative patch can race with Argo self-heal and is not the runbook. [Official trigger semantics](https://volsync.readthedocs.io/en/stable/usage/triggers.html) and the [installed-version priority rule](https://github.com/backube/volsync/blob/v0.16.0/internal/controller/statemachine/machine.go#L83) explain the two-step source change. Verify the encrypted repositories can be read with preserved keys. Snapshot allocation alone is not an off-cluster backup.
4. Restore the full data snapshot into isolated scratch or a new claim and run SQLite `PRAGMA integrity_check` on the restored database with its WAL/journals. The initial bounded local SQLite check passed below; verify restored attachments and app behavior before calling it a complete app recovery. For an explicitly app-consistent/pre-upgrade copy, stop web through reviewed Git/Argo and wait until its sole writer has stopped before capturing/uploading the complete volume; restart via Git only after success. Never copy only live `db.db` and omit WAL/journals/assets.
5. Meilisearch is a derived index but its exact rebuild procedure must pass before calling it disposable. Its own whole-volume backup is retained initially. Pin the engine version and verify the native Karakeep reindex operation during restore acceptance; do not assume an image downgrade can read a newer index.
6. For full application acceptance, restore into an isolated new namespace/claim with no production ingress, email, webhooks, crawler access or inference. Verify existing owner login, bookmark/attachment counts and checksums, search/reindex, app key recovery and export. Record snapshot ID/time, restore result and recovery scope privately; preserve the original claims. These complete application workflows have not been exercised by the bounded local SQLite check.

Repeat isolated restores monthly and take a fresh app-consistent copy before upgrades. The initial archive/SQLite result below does not establish an RPO/RTO guarantee or complete app restore. The app has single-node SQLite/RWO availability and short Recreate outages; HA would require a different supported architecture and is not silently introduced.

## First-start acceptance evidence

A later read-only web inspection confirmed `/data/db.db` (626688 bytes), `/data/db.db-wal`, `/data/queue.db` and its WAL/journal files exist. The pinned app deliberately preserves this callback route. `/api/auth/providers` is an obsolete NextAuth probe and returns 404. No human login was completed or identity created by that check.

## Bounded local SQLite restore exercise

The initial SQLite recovery proof can run outside Kubernetes, using Restic's read-only `--no-lock snapshots`, `ls` and `dump` commands against the existing encrypted repository. No temporary cluster workload, PVC, ReplicationDestination, application or identity is required.

1. After the data source manual tag finishes, choose its actual nonempty Restic snapshot taken after web startup. Read only the existing namespace-bound repository secret into the verifier process's memory; pass it to Restic through that subprocess environment, without printing values or writing an environment file. Use an official pinned Restic binary verified against its release checksums.
2. List that snapshot privately, then dump `db.db`, `queue.db` and each matching WAL/journal from the same immutable snapshot into a local task scratch directory with mode0700 and files mode0600. Do not open, mount or write the production PVC. Omit transient SHM so SQLite rebuilds it from the restored WAL on scratch.
3. Run SQLite `PRAGMA integrity_check` and require a nonempty schema for each restored database. Missing databases, empty schemas or corrupt databases fail verification. Report only snapshot/time, table/file counts and integrity results; do not print user/session contents or decrypted bookmark data. Stop after verification and preserve only the needed private recovery evidence.
4. Record the actual result separately. This proves the initial encrypted archive and both SQLite structures; first-owner login, bookmark/attachment workflows and search rebuild remain separate acceptance checks. A zero-user initial database is expected before the owner's own OIDC enrollment. This is not a claim that a complete Karakeep deployment was restored and used.
5. Remove the source `manual` tags through reviewed Git/Argo after the accepted copies, then confirm both cron `nextSyncTime` values return. Preserve the original app claims, source repositories, source caches, all sealed keys and backups.
