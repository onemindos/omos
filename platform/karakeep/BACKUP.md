# Karakeep persistence and recovery gate

No Karakeep backup is claimed live or restore-tested. Keep all Deployments at zero until the coordinator accepts this plan and provisions the app's backup destination. The full `/data` volume is authoritative: SQLite, its journals/WAL, assets/attachments, background-job state and related app files belong together. Keep the strict SealedSecret and the cluster sealing-key recovery separately. User bookmark JSON/ZIP exports produced by the app are useful portability exports, not a complete users/config/assets disaster-recovery backup.

## Before real use

1. Record `karakeep/data-pvc` (20Gi) and `karakeep/meilisearch-pvc` (5Gi) UIDs/PVs after manual Argo creation; both use do-block-storage and explicit Prune=false, Delete=false, Replace=false, Force=false protections. Do not delete the namespace or claims on uninstall.
2. Extend the EXISTING Argo-owned VolSync pipeline using [its runbook](../backups/volsync/README.md), not a second backup server. Provision a dedicated strict SealedSecret `karakeep/karakeep-data-restic`, keys `RESTIC_REPOSITORY`, `RESTIC_PASSWORD`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, scoped to the approved DigitalOcean Spaces backup prefix. These AWS-named fields are the existing restic S3-protocol contract, not AWS service credentials. No backup credential is supplied here; do not copy broad live values or use placeholders.
3. Add an owned ReplicationSource for `data-pvc`, local storageClass `do-block-storage`, CopyMethod Snapshot, with app-consistent quiescing, the existing CSI VolumeSnapshotClass, explicit retention and reviewed backup-pod budgets/egress. Review its exact CRD schema and the current existing pipeline before source integration; no speculative CRD fields are committed in this preparation. A missing destination/SealedSecret/restore record blocks normal usage. Keep this as a separate reviewed backup activation so the manual app does not start backups automatically.
4. For the initial accepted backup: scale web to zero through reviewed Git/Argo, wait until the sole writer has stopped and its volume is detached, capture the full data snapshot and off-cluster encrypted copy, verify completion, then restart only after that check. Repeat quiesced backups until a tested SQLite-consistent online procedure replaces it. Do not copy only a live `db.db` while leaving WAL/journal or assets behind. Snapshot allocation alone is not an off-cluster backup.
5. Meilisearch is a derived index but its exact rebuild procedure must pass before calling it disposable. Initially capture its quiesced volume as a second source or supported Meilisearch dump. Pin the engine version and document the native Karakeep reindex operation during restore acceptance; do not assume an image downgrade can read a newer index.
6. Restore into an isolated new namespace/claim with no production ingress, email, webhooks, crawler access or inference. Verify SQLite integrity, existing owner login, bookmark/attachment counts and checksums, search/reindex, app key recovery and export. Record snapshot ID/time, restore result and recovery scope privately; preserve the original claims. No such acceptance has happened in this source task.

Suggested initial policy for coordinator review: daily app-consistent off-cluster data copy, 7 daily / 4 weekly / 3 monthly retention, pre-upgrade copy and monthly isolated restore. This is a proposal, not a deployed schedule or RPO/RTO guarantee. The app has single-node SQLite/RWO availability and short Recreate outages; HA would require a different supported architecture and is not silently introduced.
