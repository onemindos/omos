1. How CloudTAK's ETL System Actually Works (from source code)

Key Discovery: CloudTAK has a full ETL framework. Each data source runs as a Docker container (ETL Task) that submits GeoJSON features back to the CloudTAK API. CloudTAK then converts to CoT, pushes to TAK Server, stores in PostGIS, and renders on the map. The scheduling uses AWS Lambda + EventBridge in AWS mode, but our instance runs in docker-compose mode — meaning we need a local task runner replacement.
CloudTAK ETL Architecture (as built by dfpc-coe) ┌─────────────────────────────────────────────────────────────────────────────┐ │ ETL Task Container (Docker image, one per source) │ │ │ │ import ETL from '@tak-ps/etl'; │ │ │ │ class Task extends ETL { │ │ async control() { │ │ const data = await fetchFromSource(); // poll ADS-B, APRS, etc. │ │ await this.submit(geojsonFeatures); // → CloudTAK API │ │ } │ │ } │ └──────────────────────────────┬──────────────────────────────────────────────┘ │ HTTP POST /api/connection/:id/layer/:id/cot ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ CloudTAK API (our pod: cloudtak-api in cloudtak namespace) │ │ │ │ • Receives GeoJSON FeatureCollection │ │ • Converts to CoT via @tak-ps/node-cot │ │ • Stores features in PostGIS (persistence!) │ │ • Pushes CoT to TAK Server via @tak-ps/node-tak (TLS :8089) │ │ • Syncs to Data Sync / Mission (map visibility) │ │ • UI: Connection → Layer → enabled/disabled toggle │ └──────────────────────────────┬──────────────────────────────────────────────┘ │ TLS :8089 (node-tak) ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ TAK Server (takserver namespace) │ │ • Receives CoT events │ │ • Distributes to all connected clients (ATAK, WinTAK, WebTAK, CloudTAK) │ │ • NatsBridgePlugin → NATS tak.cot.out (bus distribution) │ └──────────────────────────────┬──────────────────────────────────────────────┘ │ NatsBridgePlugin ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ NATS Bus (tak.cot.out subject) │ │ • All CoT events available for any NATS consumer │ │ • JetStream for replay/persistence │ │ • ClickHouse sink for time-series analytics │ └─────────────────────────────────────────────────────────────────────────────┘

2. The ONE Missing Piece: Local Task Runner

The Problem: CloudTAK schedules ETL tasks via AWS Lambda + EventBridge. Our instance is in CLOUDTAK_Mode=docker-compose — no Lambda, no EventBridge, no CloudFormation. The ETL UI exists, the toggle exists, the API exists — but the INVOCATION is broken.

The Solution: One service — cloudtak-scheduler — that replaces Lambda invocation with k8s Job execution. Everything else in CloudTAK works as-is.
What We Build: cloudtak-scheduler (replaces Lambda + EventBridge) ┌─────────────────────────────────────────────────────────────────────┐ │ CloudTAK API (already running) │ │ └─ POST /api/connection/:id/layer/:id {enabled: true/false} │ │ └─ Layer config: { task: "etl-adsbx", cron: "rate(1 minute)" } │ └──────────────────────────────┬──────────────────────────────────────┘ │ reads layer configs (postgres or API poll) ▼ ┌─────────────────────────────────────────────────────────────────────┐ │ cloudtak-scheduler (NEW — single Deployment in cloudtak namespace) │ │ │ │ For each enabled Layer: │ │ • Reads cron/rate schedule │ │ • Creates k8s CronJob (or in-process timer for sub-second) │ │ • Passes env: API_URL, SigningSecret, LAYER_ID, CONNECTION_ID │ │ • Docker image = the ETL task image from Layer config │ │ │ │ On disable: removes CronJob │ │ On enable: creates CronJob │ │ On schedule change: updates CronJob │ └──────────────────────────────┬──────────────────────────────────────┘ │ spawns k8s Job per invocation ▼ ┌─────────────────────────────────────────────────────────────────────┐ │ ETL Task Pod (ephemeral k8s Job) │ │ • Runs ghcr.io/dfpc-coe/etl-adsbx (or any ETL image) │ │ • Fetches data from source API │ │ • Calls this.submit(features) → POST to CloudTAK API │ │ • Exits (Job complete) │ └─────────────────────────────────────────────────────────────────────┘

6. Why This Is 100% The Best Long-Term Path

❌ Old Path (what we had)

  • ✗ Custom Python scripts as k8s Deployments
  • ✗ Publish directly to NATS tak.cot.inject
  • ✗ No per-source toggle in UI
  • ✗ No persistence (events disappear)
  • ✗ No source tracking (all mixed in one subject)
  • ✗ ORP (40 protocols nobody asked for)
  • ✗ Custom infrastructure to maintain

✅ New Path (CloudTAK-native ETL)

  • Uses CloudTAK's built-in ETL framework
  • Per-source toggle in CloudTAK UI (already built)
  • Features stored in PostGIS (persistence)
  • Source tracked per-Layer (1:1 mapping)
  • 30+ existing ETL task images available
  • Events flow to TAK → NATS → ClickHouse
  • One small service to build (cloudtak-scheduler)
  • Rides CloudTAK's active development (v13.42)
