# ROS 2 bridge (FEATURES H3): owner proposals

Status: proposed, 2026-10-29. Code: `services/bridge/bridges/ros2/`. Decision 0004 #8
(onemind-xr) applies: each item below is a choice made to keep building, recorded for the
owner, not a settled decision.

**No new subject patterns.** The bridge uses `tel.fleet.robot.{id}.position|status`
(doctrine section 9.1, stored by `platform/nats/streams/tel.yaml` `tel.fleet.>`),
`cmd.fleet.robot.{id}.{verb}` (stored by `cmd.yaml` `cmd.>`; five-token form is
onemind-xr ONT-P4 / BUS-P2) and `evt.robot.{id}.command|task` (`evt.yaml` line 18 binds
`evt.robot.>`). Nothing here needs adding to the grammar register in PR #556 beyond a
reference to this file.

| Id | Proposal | Why | Alternative |
|---|---|---|---|
| H3-P1 | Robot verb catalogue `goto`, `hold`, `rtl`, `estop` (A3) and `estop_release` (A4, two humans). `estop` **latches**: `goto` and `rtl` are refused `precondition_failed` / `estopped` until `estop_release`; `hold` and `estop` are still accepted. `hold` cancels every Nav2 goal; `duration_s` is accepted but nothing resumes afterwards | asset-command.md section 3 lists these verbs and calls `estop_release` "bridge-defined"; a latch makes the H6 kill switch stick across a later approved goto | No latch (MAVLink bridge today: flight termination is final on the vehicle anyway) |
| H3-P2 | The adapter is Python (eclipse-zenoh + nats-py), so #550's Go verifier is ported, not imported. Proposal: move the shared test vectors (`tests/fixtures/policy_vectors.json`, produced by the policy service's own signer) to `services/schemas/command/vectors/` and have the policy service, the MAVLink bridge and this bridge all test against them | Zenoh's Go binding needs zenoh-c through cgo; the zenoh REST plugin needs `zenohd`; the research recommendation was "zenoh-python to nats-py" (drones-robots-agents.md, How it applies 6). Go `internal` packages cannot be imported across modules | Go adapter over the zenoh REST plugin (`--rest-http-port`), sharing a Go `services/bridge/internal/assetcmd` package with #550 |
| H3-P3 | Map frame anchored to WGS-84 by configuration (`MAP_ORIGIN_LAT/LON/HAE`, `MAP_X_BEARING_DEG`); `hae` is the origin height plus pose z (`meta.hae_source: map_origin`); `amcl_pose` preferred over `odom` on real robots | ROS has no geodetic pose; a site-sized tangent plane is exact enough (tests: round trip 1e-6 m) | `robot_localization` `navsat_transform` publishing `/gps/filtered` (NavSatFix) on robots with GNSS |
| H3-P4 | The entity service (PR #552) should fill `capabilities` for fleet assets (from `meta.commands_accepted` or a robot registry) and read `meta.kind` for robots | The policy service (PR #554) denies `not_capable` unless the target entity lists `onemind.task.goto.v1`; #552's `adapt/geo.go` `Fleet` sets neither, so a real robot (or drone) can never be commanded through the stack today. The H3 end-to-end test uses a stub entity service for this reason | Policy treats `commands_accepted` in the latest status as the capability list |
| H3-P5 | Least-privilege NATS user per robot bridge, in PR #562's `platform/nats/identities/identities.yaml` layout (below), and the robot ids added to the site leaf user `leaf-site-mac` | BUS-DESIGN section 6 row "ROS 2 bridge"; NATS wildcards cannot match `sim-*` partially, so ids are enumerated | Shared `bridge` user (rejected: any bridge could then move any robot) |
| H3-P6 | Edge deployment only: no image, Argo Application, cluster Secret or `docs/STACK.md` row, as for the MAVLink bridge (#550) | zenoh-bridge-ros2dds must be on the robot's DDS network (multicast discovery); omos `CLAUDE.md` "Bus Authority" puts edge bridges behind a site leaf. Credentials come from the owner keychain or the edge `.env` | A GHCR image plus a Compose file for the home server when it arrives |
| H3-P7 | Keep-out zones go into the Nav2 costmap on real robots (Nav2 `KeepoutFilter` with a filter mask generated from the geofence file, served by `map_server` / `costmap_filter_info_server`), so the planned path avoids them. The bridge checks the target and, as a cheap first pass, the straight line from the robot to the target against keep-out zones (`fence.check_path`) | Nav2 plans its own path, which can cross a keep-out zone between two allowed points; a ground robot follows that path, not a straight line. The MAVLink bridge (#550) checks the endpoint only | Bridge-side check of Nav2's planned path (`ComputePathToPose` before `NavigateToPose`), or endpoint check only as in #550 |
| H3-P8 | Once the policy service (#554) is on `main`, add a job to `test-ros2-bridge.yml` that builds `services/policy` and runs `tests/e2e/run.sh` with a pinned nats-server release | CI today runs the unit and in-process tests only; the verify-to-execute end-to-end flow is checked on the operator's machine (evidence in onemind-xr `docs/evidence/M4/H3/`) | Keep the e2e test manual |
